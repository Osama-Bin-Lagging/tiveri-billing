\sect{1. Scope and assumptions}
The prototype is designed for a 20 to 50 bed Indian hospital. A local HIS-style event records a delivered service, the billing API prices it from a payer rate card, and a running encounter collects charges. Staff can dispense a batch-tracked pharmacy item, add a room stay or package, collect an advance, issue one final invoice, record a simulated payer claim, and post actual receipts. The dashboard, receivables report, tax review and audit trail read the same PostgreSQL database.

It demonstrates OPD, IPD, emergency and day-care encounter types; self-pay, private TPA, PM-JAY, CGHS and corporate payer routes. The private insurance and PM-JAY paths are local simulations. No insurer, scheme, HIS or GST portal credentials are used. Three classroom logins give doctor, pharmacy and billing staff different actions. The password is \texttt{Demo@1234} for these invented accounts.

\sect{2. Architecture and data flow}
\begin{enumerate}
\item The Next.js page at port 3000 calls same-origin \texttt{/api} paths. Its configuration forwards those requests to FastAPI at port 8000.
\item FastAPI validates the action, runs billing rules in a database transaction and writes PostgreSQL rows. Integer paise represent money.
\item A unique \texttt{source\_event\_id} protects against duplicate HIS charges. A matching retry returns the original charge; a conflicting retry returns HTTP 409.
\item The service master, payer rate and effective tax rule determine a charge. Their price and tax values are copied onto the charge, then onto the final invoice line.
\item Payer preauthorisation and claim decisions are separate from receipts. Only an advance allocation or posted receipt reduces the invoice balance.
\item Reports read final invoices, tax snapshots, receipts and claims. The GSTR-1 JSON is a review packet, not a portal upload.
\end{enumerate}
An eventual standards-based exchange could map encounters, charge items, invoices, coverage and claims to applicable FHIR resources and NRCeS ABDM/NHCX profiles. The current API is a local teaching contract, not a certified exchange.

The final presentation includes the complete conceptual diagram from the supplied ER file, followed by enlarged views of its HIS and billing sides. The conceptual model includes RIS and LIS entities beyond the current website. The executable PostgreSQL schema below describes the prototype as implemented.

\sect{4. Backend and API contract}
The backend is \texttt{backend/app/main.py} using FastAPI, Pydantic and Psycopg. It exposes interactive schemas at \url{http://127.0.0.1:8000/docs}. Each write checks the encounter state and the relevant payer or stock rule before it commits. The complete route list and request meanings are in \texttt{docs/api\_contract.md}.

For example, an extra investigation on the seeded open OPD encounter is sent as:
\begin{lstlisting}
POST /api/his/events
Content-Type: application/json

{"encounter_id":"E-OPD-01","service_code":"XRAY",
 "quantity":1,"source_event_id":"CLASS-XRAY-001"}
\end{lstlisting}
Resend the same payload to see \texttt{duplicate: true}. Keep the event ID fixed but change quantity to see HTTP 409. The frontend performs these calls through forms; this example explains the HIS integration boundary.

\sect{5. Frontend and pharmacy GST}
The frontend is in \texttt{frontend/app}. Next.js shows a single patient workspace with three role choices: Doctor, Pharmacy and Billing desk. The Doctor saves a note, provisional ICD-10, service event and prescription. Pharmacy dispenses a matching order and sees the product tax and stock batch. Billing adds an IPD room stay, works through simulated payer steps and generates the itemised invoice on the same page. It calls FastAPI through the same-origin \texttt{/api} rewrite.

The pharmacy flow selects an item and unexpired batch, checks quantity, posts the dispense and stores the tax rule used at that moment. The charge master keeps an item code, description, HSN/SAC review field, tax category, effective GST setting, and stock batch. The sample \texttt{MED-A} is an invented Rs 100 training medicine. In a separate OPD sale, two units have a Rs 200 base, 5\% GST of Rs 10 and a Rs 210 total. The nil example is a generic contraceptive product under HSN 3006, not a branded drug. When a medicine is part of qualifying inpatient treatment, the demo records it under the exempt healthcare supply instead. An unclassified item is blocked from final invoicing until reviewed.

Qualified healthcare services are generally exempt under the applicable GST notification. The CBIC rate table also has a specific conditional 5\% entry for certain non-ICU rooms above Rs 5,000 per day. The supplied marketing article's blanket 18\% statement is not used. Actual medicine and device HSN classification must be reviewed item by item against the current schedule. The demo GSTR-1 packet has Tables 4, 7, 8, 12 and 13 for review; the official portal guide includes exempt supply reporting in Table 8. No government upload occurs.

\sect{6. Run locally and test}
\textbf{Fastest route with Docker Desktop.} From the repository root:
\begin{lstlisting}
docker compose up --build
\end{lstlisting}
Open \url{http://127.0.0.1:3000}. The three services are Next.js, FastAPI and PostgreSQL. PostgreSQL binds only to local port 55433. The Compose setup is supplied for repeatability; Docker was unavailable on the development computer, so this exact container path was not run there.

\textbf{Native Windows route used for testing.} Install Node.js 24, Python 3.12 and PostgreSQL 16. Create a database named \texttt{tiveri\_demo} and a user with rights to create tables. In terminal 1 from the repository root:
\begin{lstlisting}
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
$env:DATABASE_URL = "postgresql://USER:PASSWORD@127.0.0.1:5432/tiveri_demo"
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
\end{lstlisting}
In terminal 2:
\begin{lstlisting}
cd frontend
npm ci
npm run dev
\end{lstlisting}
The frontend is at \url{http://127.0.0.1:3000}; API documentation is at \url{http://127.0.0.1:8000/docs}. If using a different API address, set \texttt{API\_INTERNAL\_URL} before starting or building Next.js.

Check the native stack and restore the demo data:
\begin{lstlisting}
curl http://127.0.0.1:8000/api/health
.\.venv\Scripts\python.exe -m pytest tests\test_api.py -q
cd frontend
npm run build
\end{lstlisting}
The database-backed tests cover OPD, TPA, PM-JAY, stock, room, package, payment, refund, tax review and receivables. The website was also exercised in a browser against the live local API and database. The billing desk has a Reset demo button to restore the invented cases; the action signs out every role.

\sect{8. Private AWS EC2 classroom deployment}
This is a deployment plan for the synthetic demo; it was not deployed to AWS during development. Keep all application ports bound to loopback and reach the site by SSH tunnel.

\begin{enumerate}
\item Create an Ubuntu EC2 instance with an SSH key pair and sufficient disk space for the Docker images and PostgreSQL volume. In its security group, allow inbound TCP 22 from \emph{My IP} only. Do not add inbound 3000, 8000 or 55433.
\item Connect with the username shown by EC2 for that AMI, commonly \texttt{ubuntu}. Install Docker Engine and the Compose plugin using Docker's current Ubuntu installation guide linked in Section 10.
\item Install Git, clone the repository and start the three services:
\end{enumerate}
\begin{lstlisting}
sudo apt-get update
sudo apt-get install -y git
git clone https://github.com/sreehariX/tiveri-billing.git
cd tiveri-billing
sudo docker compose up --build -d
sudo docker compose ps
curl http://127.0.0.1:8000/api/health
\end{lstlisting}
On the presentation laptop, open a second terminal:
\begin{lstlisting}
ssh -i KEY.pem -L 3000:127.0.0.1:3000 ubuntu@PUBLIC_IP
\end{lstlisting}
Keep the tunnel open, then visit \url{http://127.0.0.1:3000} on the laptop. The exact username and key permissions depend on the AMI and client. The Compose file binds all exposed ports to \texttt{127.0.0.1}, so the website is reachable through the tunnel rather than a public application port.

The Compose password is a demo value. Do not place real patient information on this host. A real deployment requires stronger authentication, roles, TLS, secret storage, encryption, backups, monitoring, retention rules, approved rates and authorised HIS/payer integrations.

\sect{9. Future scope}
For a larger hospital, add dedicated roles and approvals, multi-location configuration, deeper corporate credit rules, insurer-specific document templates, actual scheme and payer sandbox integrations, inventory procurement, stronger report reconciliation, performance testing, migration tooling and disaster recovery. Each integration should be validated against its current official contract and the hospital's policy.
